## 추가 작업 - 사업자 접근 보호와 권한 필드 축소

### Work Summary

사업자 카탈로그가 공개 View를 직접 읽는 구조였기 때문에, 이후 `catalog_public_products`의 브라우저 직접 조회 권한을 회수할 수 있도록 사업자 전용 8자리 접근 코드와 Edge Function 기반 세션 흐름으로 전환했다. 동시에 센터 응답과 화면에서 더 이상 확정 권한에 포함되지 않는 컬럼을 제거해 역할별로 필요한 데이터만 내려가도록 정리했다.

### Work Completed

* `catalog-business` Edge Function을 새로 추가해 `login`과 `products` action을 분리 구현했다. `BUSINESS_ACCESS_CODE`와 `BUSINESS_SESSION_SECRET`을 사용하며, 8자리 코드 검증, timing-safe 비교, 실패 지연, 30일 서명 세션, CORS/OPTIONS 응답, 서비스 역할 키 기반 상품 조회를 적용했다.
* 사업자 상품 응답은 `id`, `name_ko`, `name_pt`, `business_price`, `consumer_price`, `brazil_price`, `is_set`, `pack_quantity`만 반환하도록 했다. `updated_at`은 사업자 응답에서 제외했다.
* 기존 `catalog-center` Edge Function은 로그인 방식과 세션 동작을 유지하면서 응답 컬럼을 `id`, `name_ko`, `name_pt`, `handling_fee`, `business_price`, `consumer_price`, `brazil_price`, `brazil_pv`, `is_set`, `pack_quantity`로 축소했다.
* 센터 타입, 표, 모바일 카드, 인쇄 화면에서 `korea_pv`, `korea_price`, `weight`, `memo`, `updated_at` 의존성을 제거했다.
* `/catalog` 사업자 화면은 더 이상 Supabase View를 직접 조회하지 않고, 사업자 접근 코드 입력 후 `catalog-business`에서 받은 세션 토큰으로 상품을 불러오도록 변경했다.
* 사업자 세션은 `catalog_business_session`, 센터 세션은 `catalog_center_session`에 따로 저장해 로그아웃과 만료 처리가 서로 영향을 주지 않게 했다.
* README에 Supabase Dashboard 기반 Edge Function 생성/갱신 절차와 최종 수동 보안 단계인 `revoke select on public.catalog_public_products from anon, authenticated;` 실행 절차를 추가했다.
* `npm.cmd run build`로 TypeScript와 Vite 프로덕션 빌드를 확인했다.

### Decisions

사업자와 센터는 같은 8자리 코드 흐름을 쓰지만 권한과 반환 필드가 다르므로 하나의 Edge Function에 role 분기를 추가하지 않고 `catalog-business`와 `catalog-center`를 분리했다. 이렇게 해야 비즈니스 코드와 센터 코드, 세션 secret, localStorage key가 섞이지 않고, 각 함수의 select 목록도 감사하기 쉽다.

사업자 상품 조회는 `catalog_products`를 서비스 역할 키로 읽되 반드시 `is_visible = true` 조건을 적용하기로 했다. 공개 View 권한을 최종적으로 회수해도 Edge Function은 계속 동작해야 하며, 브라우저가 View 권한에 의존하지 않도록 만드는 것이 이번 변경의 핵심이기 때문이다.

센터 화면에서는 확정 권한에 남은 가격/PV 필드만 보여 주기로 했다. 한국 PV, 한국 가격, 중량, 메모, 업데이트 시각은 응답에서 제거되므로 프론트엔드 타입과 표시 로직에서도 함께 제거해 숨겨진 컬럼에 의존하지 않게 했다.

### Current Status

사업자 카탈로그는 저장된 사업자 세션이 없으면 상품 데이터를 요청하지 않고 접근 코드 화면을 먼저 표시한다. 세션이 유효하면 새 Edge Function을 통해 상품을 불러오며, 401 응답이나 만료 세션은 사업자 로그인 화면으로 되돌린다. 센터 카탈로그는 기존 코드/세션 흐름을 유지하면서 축소된 센터 필드만 표시한다.

코드 검색으로 프론트엔드와 빌드 산출물에 `BUSINESS_ACCESS_CODE`, `BUSINESS_SESSION_SECRET`, `SUPABASE_SERVICE_ROLE_KEY`, `catalog_public_products`가 남지 않은 것을 확인했다. `catalog_public_products`는 README의 최종 수동 revoke SQL에만 남아 있다. 제거 대상 센터 필드인 `korea_pv`, `korea_price`, `memo`, `updated_at`도 `src`, `supabase`, README에서 더 이상 발견되지 않았다.

### Next Steps

* Supabase Dashboard에서 `BUSINESS_ACCESS_CODE`, `BUSINESS_SESSION_SECRET`, `CENTER_ACCESS_CODE`, `CENTER_SESSION_SECRET`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`가 설정되어 있는지 확인한다.
* Dashboard에서 `catalog-business`를 생성하고 `catalog-center`를 갱신한 뒤 프론트엔드를 배포한다.
* 사업자와 센터 접근을 실제 코드로 테스트한 다음, 마지막 단계로 Supabase SQL Editor에서 공개 View 조회 권한 revoke SQL을 실행한다.
* revoke 이후에도 `/catalog` 사업자 접근과 `/catalog/center` 센터 접근이 Edge Function을 통해 계속 동작하는지 다시 확인한다.

## 추가 작업 - 애터미 모바일 UI 톤과 바로가기 안내

### Work Summary

모바일 사용 비중이 높고 사용자가 웹앱 설치 개념에 익숙하지 않다는 전제를 바탕으로, 화면을 애터미 사이트에 가까운 흰 배경과 밝은 블루 중심의 미니멀한 톤으로 정리했다. 앱을 설치해야 한다는 오해를 줄이기 위해 로그인 화면과 상품 화면에 휴대폰 첫 화면 바로가기 안내 흐름을 추가했다.

### Work Completed

* 상단 헤더를 애터미 블루 앱바 형태로 바꾸고 중앙에 앱 이름이 보이도록 했다.
* 로그아웃, 언어 전환, 바로가기 안내 진입점을 우측 `⋮` 메뉴 구조로 정리했다.
* 로그인 화면 하단에 설치 앱이 아니라 바로가기로 사용할 수 있다는 안내 문구를 한국어와 포르투갈어로 추가했다.
* 상품 화면에는 첫 접속 후 한 번만 보이는 바로가기 안내 배너를 추가하고, 닫으면 `localStorage`에 기록해 다시 표시되지 않게 했다.
* 바로가기 안내 다이얼로그에 안드로이드 크롬과 아이폰 사파리 기준 설명을 한국어와 포르투갈어로 제공했다.
* 기존에 깨져 보이던 한국어/포르투갈어 번역 문자열과 언어 전환 라벨을 정상 문자열로 정리했다.
* `npm.cmd run build`로 TypeScript와 Vite 프로덕션 빌드를 확인했다.
* 390px 모바일 뷰포트에서 로그인 화면의 헤더, 안내 문구, 한국어 전환, 가로 스크롤 여부를 확인했다.

### Decisions

사용자층이 "웹앱", "PWA", "설치"라는 표현을 이해하지 못할 가능성이 높으므로, 화면 문구는 "휴대폰 첫 화면에 바로가기 만들기" 중심으로 잡았다. 자동 설치 버튼은 브라우저와 기기 조건에 따라 보이지 않을 수 있어, 기능 버튼만 믿지 않고 브라우저 메뉴를 통한 수동 안내를 항상 제공하기로 했다.

헤더는 별도 로고 이미지 없이 앱 이름을 중앙에 두는 방식으로 구현했다. 현재 앱은 업무용 가격표 도구이므로 브랜드 느낌은 색상과 여백으로만 전달하고, 장식적 요소는 추가하지 않는 것이 모바일 가독성과 반복 사용에 더 적합하다고 판단했다.

### Current Status

로그인 화면에서는 선택 언어에 맞는 설치 오해 방지 문구가 보이며, 상품 화면에 진입하면 바로가기 안내 배너와 도움말 다이얼로그를 사용할 수 있다. 상단 앱바는 모바일 폭에서 가로 스크롤 없이 표시되는 것을 확인했다.

상품 화면 배너는 실제 접근 세션이 있어야 전체 흐름을 확인할 수 있으므로, 이번 검증에서는 빌드와 로그인 화면 기준 레이아웃 확인까지만 완료했다.

### Next Steps

* 실제 사업자 접근 코드로 상품 화면에 진입해 바로가기 배너, 도움말 다이얼로그, 닫기 후 재표시 방지 동작을 확인한다.
* 실제 안드로이드 크롬에서 브라우저 메뉴 문구가 안내와 일치하는지 확인한다.
* 필요하면 상단 앱 이름을 최종 서비스명에 맞춰 조정한다.

### Next Steps

* 실제 모바일 business/center 화면에서 접힌 카드 우측 가격이 소비자 가격과 일치하는지 확인한다.

* 관리자 화면에서 한국어/포르투갈어 상품명 검색을 클라이언트 상태 기준으로 즉시 필터링하도록 했다.
* 표시 중인 상품 목록과 숨긴 상품 목록을 분리하고, 숨긴 상품은 별도 섹션을 열었을 때만 보이게 했다.
* 상품 생성/수정 폼에서 `name_ko`, `name_pt`, 가격/PV/무게/수량, 세트 여부, 표시 여부, 메모를 편집할 수 있게 했다.
* `id`, `created_at`, `updated_at`는 수정 payload에 포함하지 않고, `id`만 편집 화면의 참고 정보로 표시했다.
* 빈 숫자 입력값은 `0`으로 바꾸지 않고 `null`로 저장하도록 파싱 규칙을 분리했다.
* `pack_quantity`도 빈 값은 `null`로 저장하며, 기존 표시 컴포넌트 규칙에 따라 1 이하 값은 수량 배지를 표시하지 않는다.
* 상품 숨김은 삭제가 아니라 `is_visible=false` 업데이트로 처리하고, 숨기기 전 확인 다이얼로그를 표시하도록 했다.
* 숨긴 상품 복구는 `is_visible=true` 업데이트로 처리하고, 성공 시 로컬 상품 상태에 즉시 반영되게 했다.
* 관리자 로그인/권한 없음 화면과 관리자 인증 훅의 깨진 한국어 문구를 정상 문구로 정리했다.
* 관리자 화면 스타일을 모바일 우선으로 추가해 큰 터치 영역, 조밀한 카드 목록, 명확한 저장/취소/숨김 버튼을 제공했다.

### Decisions

관리자 CRUD는 프론트엔드에서 새 service-role 클라이언트를 만들지 않고 기존 authenticated Supabase 클라이언트만 사용한다. 전체 상품 필드 읽기와 수정 권한은 Google 세션, `workspace_members`, RLS 정책, `public.is_catalog_admin()`에 맡기는 구조가 보안 경계를 가장 명확하게 유지하기 때문이다.

상품 제거는 하드 삭제가 아니라 `is_visible` 플래그 변경으로만 처리하기로 했다. 가격표에서 빠져야 하는 상품이라도 과거 가격과 상품 기록은 운영상 다시 확인하거나 복구할 수 있어야 하며, business/center Edge Function이 이미 `is_visible=true` 조건으로 상품을 제한하므로 같은 모델을 관리자 화면에서도 따르는 것이 안전하다.

관리자 전용 필드인 `korea_pv`, `korea_price`, `weight`, `memo`, `is_visible`, 생성/수정 시각은 business/center Edge Function 응답에 추가하지 않았다. 사업자와 센터 화면의 필드 권한은 기존 구조를 유지하고, 관리자 화면만 직접 `catalog_products`를 조회하도록 분리했다.

모바일 관리자는 한 손으로 상품을 찾고 빠르게 수정할 가능성이 높으므로 목록 카드에는 모든 필드를 넣지 않고 이름, 주요 가격, 세트/수량 배지만 노출했다. 상세 필드는 선택 후 폼에서 수정하도록 해 목록의 스캔 속도를 우선했다.

### Current Status

`#/admin`에서 관리자 권한이 확인되면 상품 관리 화면이 표시된다. 화면 안에서 상품 검색, 새 상품 추가, 기존 상품 수정, 상품 숨김, 숨긴 상품 보기, 복구, 로그아웃을 수행할 수 있다. 저장/생성/숨김/복구는 전체 페이지 새로고침 없이 로컬 상품 상태를 갱신한다.

`npm.cmd run build`는 통과했다. 코드 검색으로 프론트엔드에 `SUPABASE_SERVICE_ROLE_KEY` 또는 service-role 클라이언트가 추가되지 않은 것을 확인했다. `.delete()` 호출도 추가되지 않았다. 기존 `catalog-business`와 `catalog-center` Edge Function은 계속 `is_visible=true` 조건으로 상품을 반환한다.

실제 RLS 정책이 관리자 CRUD를 허용하는지, 비관리자 authenticated 사용자의 직접 `catalog_products` 접근을 차단하는지는 원격 Supabase 정책에 의존하므로 실제 관리자/비관리자 계정으로 추가 확인이 필요하다.

### Next Steps

* 실제 관리자 Google 계정으로 `#/admin`에 접속해 상품 목록 로드, 생성, 수정, 숨김, 복구를 테스트한다.
* 비관리자 Google 계정으로 `#/admin` 권한 없음 화면이 유지되는지 확인한다.

* business/center 8자리 로그인과 숨김 상품 미노출 동작을 실제 배포 환경에서 확인한다.

## 추가 작업 - 센터 공개 진입 URL 추가

### Work Summary

센터 사용자가 공유받을 짧은 주소인 `/center`로 접속해도 기존 해시 라우트 `/#/catalog/center`의 센터 카탈로그 로그인 화면으로 바로 이동하도록 정적 리다이렉트 페이지를 추가했다. 기존 해시 라우터 구조는 변경하지 않고, 정적 호스팅에서 짧은 URL만 진입점으로 제공하는 방식으로 처리했다.

### Work Completed

* `public/center/index.html`을 추가해 `/center/` 요청이 즉시 `/#/catalog/center`로 이동하도록 했다.
* 정적 서버가 확장자 없는 `/center` 요청을 직접 파일로 해석하는 경우도 대응하기 위해 같은 리다이렉트 내용을 `public/center.html`에도 추가했다.
* 두 정적 페이지 모두 `window.location.replace("/#/catalog/center")`, meta refresh fallback, visible fallback link를 포함했다.
* 검색 엔진 색인을 막기 위해 `meta name="robots" content="noindex"`를 추가했다.
* 페이지 언어는 포르투갈어(`pt-BR`)로 지정했다.
* `npm.cmd run build`를 실행해 프로덕션 빌드가 성공하는지 확인했고, `dist/center/index.html`과 `dist/center.html`이 생성되는 것을 확인했다.
* Vite preview에서 `/center`, `/center/`, `/#/catalog/center`가 모두 센터 로그인 화면으로 도달하는 것을 브라우저로 확인했다.
* `/` 비즈니스 카탈로그 진입 화면과 `/#/admin` 관리자 로그인 화면이 기존대로 유지되는 것을 확인했다.

### Decisions

요청의 핵심은 라우터 전환이 아니라 공유용 짧은 URL을 제공하는 것이므로, React 라우팅을 browser-history 방식으로 바꾸지 않고 `public` 정적 파일만 추가했다. `replace`를 사용한 이유는 브라우저 뒤로 가기 시 리다이렉트 페이지만 반복해서 다시 열리는 흐름을 막기 위해서다.

Vite preview에서는 `/center/`가 `public/center/index.html`로 처리되지만, `/center`는 서버의 SPA fallback 정책에 따라 앱 셸로 직접 떨어질 수 있었다. 실제 공유 URL이 slash 없는 `/center`이므로, 정적 호스팅 환경과 로컬 preview 양쪽에서 더 안정적으로 동작하도록 `public/center.html`도 같은 내용으로 추가했다.

### Current Status

센터 공개 진입 URL은 빌드 산출물 기준으로 `/center`와 `/center/` 모두 `/#/catalog/center`에 도달한다. 기존 센터 해시 라우트도 그대로 동작하며, 비즈니스와 관리자 화면의 라우트 분기는 변경하지 않았다.

저장된 센터 세션은 같은 origin의 `localStorage`를 사용하는 구조이고 리다이렉트는 같은 origin 안에서 hash만 바꾸므로, 리다이렉트 페이지 자체가 세션을 삭제하거나 새 origin으로 이동시키지 않는다. 다만 이번 브라우저 자동화 환경에서는 임시 `localStorage` 값을 직접 주입하는 동작이 보안 정책으로 차단되어, 실제 저장 세션을 주입한 end-to-end 확인은 수행하지 못했다.

### Next Steps

* 배포 후 `https://price.nangok.app/center`와 `https://price.nangok.app/center/`가 모두 센터 로그인 화면 또는 저장된 센터 세션의 상품 화면으로 이동하는지 실제 도메인에서 확인한다.
* 실제 센터 계정 세션이 남아 있는 브라우저에서 `/center` 공유 URL을 열어 상품 화면으로 바로 이어지는지 최종 확인한다.

* `npm.cmd run build`로 TypeScript와 Vite 프로덕션 빌드가 통과하는지 확인했다.

### Decisions

관리자 화면은 상품 수정, 숨김, 복구 같은 운영 액션이 있어 사업자/센터 조회 컴포넌트를 그대로 쓰기는 어렵다. 다만 문구와 컬럼 라벨은 같은 상품 도메인의 표현이므로 컴포넌트 안에 분산시키지 않고 `i18n`에서 관리하는 것이 맞다고 판단했다.

이번 작업에서는 화면 구조를 큰 폭으로 재작성하지 않고, 먼저 문구의 출처를 통합하는 좁은 변경만 적용했다. 이후 관리자 표/카드 자체를 센터 화면의 `columnConfig` 기반 구조와 더 가깝게 합치는 작업을 별도로 진행할 수 있다.

### Current Status

관리자 화면의 주요 표시 문구와 필드 라벨은 `src/i18n.ts`의 `dictionary.ko.admin`을 기준으로 관리된다. 포르투갈어 관리자 문구도 같은 구조로 추가해 두었지만, 현재 관리자 화면은 한국어 고정 흐름을 유지한다.

빌드는 성공했다. UI 동작은 바꾸지 않았으므로 상품 생성, 수정, 숨김, 복구 흐름은 기존 구조를 그대로 사용한다.

### Next Steps

* 관리자 화면에도 언어 전환이 필요해지면 현재 추가한 `dictionary.pt.admin` 값을 실제 화면 언어 상태와 연결한다.
* 관리자 표/카드 컬럼 정의를 센터/사업자와 같은 `columnConfig` 계열로 통합할지 검토한다.
* 이슈 #4의 남은 모바일 UI 개선 항목인 수정 폼 팝업화, 저장 후 닫기, 접힌 카드의 소비자 가격 표시, 업데이트 날짜 표시를 이어서 처리한다.

## 추가 작업 - 관리자 수정 폼 모달/하단 시트 전환

### Work Summary

관리자 상품 수정 폼이 목록 위쪽에 인라인 카드로 열리면서, 화면 하단의 상품을 수정할 때 사용자가 다시 상단으로 이동해야 하는 문제가 있었다. 상품 목록의 위치와 관계없이 즉시 편집할 수 있도록 PC에서는 중앙 모달, 모바일에서는 하단 시트 형태로 폼을 띄우게 변경했다.

### Work Completed

* `AdminProductForm`을 인라인 섹션에서 `role="dialog"`와 `aria-modal="true"`를 가진 오버레이 구조로 바꿨다.
* PC 화면에서는 폼이 화면 중앙에 최대 폭을 가진 모달로 열리고, 내용이 길면 모달 내부에서 스크롤되도록 했다.
* 모바일 화면에서는 폼이 화면 하단에 붙은 시트처럼 열리며, 안전 영역을 고려해 하단 여백을 확보했다.
* 배경 클릭, 상단 닫기 버튼, `Esc` 키, 기존 취소 버튼으로 폼을 닫을 수 있게 했다. 저장/처리 중에는 닫기 동작을 막아 중간 상태가 끊기지 않도록 했다.
* 폼이 열릴 때 한국어 상품명 입력란에 자동으로 초점이 가도록 했다.
* 출력 화면에서는 관리자 수정 폼 오버레이와 확인 다이얼로그가 인쇄되지 않도록 했다.
* `npm.cmd run build`로 TypeScript와 Vite 프로덕션 빌드가 통과하는지 확인했다.
* 로컬 Vite dev 서버를 `http://127.0.0.1:5173/#/admin`에서 열 수 있도록 실행했고, HTTP 200 응답을 확인했다.

### Decisions

새 상품 추가와 기존 상품 수정은 같은 폼을 쓰는 구조를 유지했다. 문제의 핵심은 폼 컴포넌트의 재사용 자체가 아니라 표시 위치였으므로, 데이터 저장 흐름과 관리자 상품 상태 관리는 건드리지 않고 표시 레이어만 오버레이로 분리했다.

확인 다이얼로그와 같은 어두운 배경 오버레이 패턴을 사용하되, 상품 폼은 입력 필드가 많기 때문에 PC에서는 더 넓은 중앙 모달로 두었다. 모바일에서는 화면 중앙 모달보다 하단 시트가 엄지 조작과 긴 폼 스크롤에 더 적합하다고 판단했다.

### Current Status

관리자 상품 폼은 목록 위치와 관계없이 화면 위 오버레이로 열린다. PC에서는 중앙 모달, 모바일에서는 하단 시트 형태가 적용된다. 빌드는 성공했고, 로컬 dev 서버에서 관리자 라우트 응답도 확인했다.

실제 관리자 Google 세션과 Supabase 상품 데이터가 필요한 생성/수정/숨김/복구의 전체 저장 흐름은 이번 로컬 확인에서 별도로 실행하지 않았다.

### Next Steps

* 실제 관리자 계정으로 모바일 기기에서 하단 시트의 높이, 키보드 표시 시 스크롤, 닫기 동작을 확인한다.
* 이슈 #4의 남은 항목인 수정 저장 후 폼 닫기, 접힌 카드 소비자 가격 표시, 업데이트 날짜 표시를 이어서 처리한다.
