# 가격표 앱 홈 화면 아이콘 안내 문구 개선 작업 로그

## 작업 배경

가격표 앱의 세 가지 권한별 주소가 안드로이드에서 홈 화면 아이콘으로 정상 추가되는지 확인하려고 실제 사용자 테스트를 진행했다.

테스트 과정에서 예상하지 못한 문제가 연속으로 확인되었다.

- 카카오톡에서 받은 링크를 Chrome이 아닌 카카오톡 내부 브라우저로 열었다.
- `바로가기 만드는 방법` 버튼을 누르면 아이콘이 자동으로 생성된다고 이해했다.
- `바로가기`, `홈 화면`, `앱처럼 열기` 등의 표현 자체를 낯설어했다.
- `안드로이드폰`보다 `삼성폰`이라는 표현을 더 쉽게 이해했다.
- 브라우저 앱이 별도로 존재하며 Chrome, Safari 등 여러 종류가 있다는 개념이 없었다.
- 아이콘 추가 과정에서 공유 메뉴나 추가 확인 버튼을 찾지 못했다.

이를 통해 기존 안내는 웹앱과 브라우저 개념을 이미 아는 사람만 이해할 수 있다는 점을 확인했다.

## 작업 목표

- 웹앱 개념을 모르는 사용자도 안내만 보고 홈 화면 아이콘을 만들 수 있게 한다.
- 작은 스마트폰 화면에서도 읽기 쉽도록 문장을 짧게 만든다.
- 기술 용어보다 사용자가 실제로 보는 앱 이름과 버튼 이름을 사용한다.
- 카카오톡·WhatsApp 내부 브라우저에서는 아이콘을 만들 수 없다는 점을 먼저 알린다.
- 한국어와 포르투갈어 안내 문구를 같은 구조로 맞춘다.

## 주요 변경 사항

### 1. 자동 설치로 오해할 수 있는 표현 수정

기존의 `바로가기 만드는 방법`은 버튼을 누르면 아이콘이 자동 생성되는 기능처럼 보일 수 있었다.

다음과 같이 변경했다.

- `홈 아이콘 추가하는 방법`
- `홈 화면에 아이콘 만들기`

또한 아이콘은 자동 설치되는 것이 아니라 사용자가 브라우저 메뉴에서 직접 추가해야 한다는 전제로 안내 구조를 바꿨다.

### 2. 추상적인 기술 용어 축소

다음 표현은 사용자에게 개념 부담을 줄 수 있어 가급적 피했다.

- 바로가기
- 웹앱
- 앱처럼 열기
- 브라우저에서 다시 열기

대신 실제 행동과 결과가 바로 보이도록 표현했다.

- `휴대폰 화면에 아이콘을 만들어 두면`
- `다음부터는 그 아이콘만 눌러서 바로 열 수 있습니다`
- `Chrome(크롬) 앱 열기`
- `Safari(사파리) 앱 열기`

### 3. 카카오톡·WhatsApp 내부 브라우저 문제 명시

메신저 안에서 열린 화면에서는 홈 화면 아이콘을 만들 수 없다는 점을 안내 첫 문장에 넣었다.

```ts
shortcutHelpIntro:
  "카카오톡이나 WhatsApp에서는 아이콘을 만들 수 없습니다. 링크를 복사한 뒤 아래 순서대로 따라 해 주세요.",
```

`주소`보다 사용자가 메시지에서 실제로 접하는 표현에 가까운 `링크`를 사용했다.

### 4. 휴대폰 종류 표현 변경

`안드로이드`라는 용어를 모르는 사용자도 자기 안내를 찾을 수 있도록 제목을 다음과 같이 변경했다.

```ts
shortcutAndroidTitle: "삼성폰·안드로이드폰",
shortcutIosTitle: "아이폰",
```

### 5. 앱 이름 한영 병기

휴대폰 화면에 표시되는 앱 이름과 사용자가 익숙한 한국어 발음을 함께 보여주기 위해 다음과 같이 표기했다.

- `Chrome(크롬)`
- `Safari(사파리)`

### 6. 단계별 줄바꿈 적용

모든 단계가 한 문단으로 붙지 않도록 문자열에 `\n`을 넣었다.

```ts
shortcutAndroidSteps:
  "1. Chrome(크롬) 앱 열기\n2. 주소창에 링크를 붙여넣고 이동\n3. 가격표 사이트가 열리면 주소창 옆의 점 세 개(⋮) 메뉴 누르기\n4. ‘홈 화면에 추가’ 누르기\n5. ‘바로가기 만들기’ 또는 ‘설치’를 누른 뒤 ‘추가’ 누르기",
```

화면 출력 요소에는 줄바꿈이 유지되도록 `white-space: pre-line` 또는 Tailwind의 `whitespace-pre-line`을 적용해야 한다.

### 7. 위치 변화에 덜 민감한 문구 사용

Chrome 메뉴 위치를 `오른쪽 위`라고 고정하지 않고 다음과 같이 변경했다.

- `주소창 옆의 점 세 개(⋮) 메뉴`

브라우저 업데이트로 주소창이나 메뉴 위치가 바뀌어도 안내문을 계속 사용할 수 있도록 했다.

### 8. 마지막 확인 단계 추가

안드로이드에서는 `홈 화면에 추가`를 누른 뒤에도 추가 확인이 필요할 수 있다.

표시되는 방식에 따라 다음 중 하나가 나타날 수 있어 둘 다 안내에 포함했다.

- `바로가기 만들기`
- `설치`
- 이후 `추가`

## 포르투갈어 적용

한국어와 동일한 구조로 포르투갈어 문구도 작성했다.

- 짧은 명령형 사용
- 실제 앱 이름과 메뉴 이름 사용
- WhatsApp 내부에서는 아이콘을 만들 수 없다는 점 명시
- Samsung과 Android를 함께 표기
- Android와 iPhone 절차를 각각 번호로 분리

## 결정 사항

- 안내문은 기술적으로 정교한 설명보다 실제 사용 성공률을 우선한다.
- 사용자가 웹앱, 브라우저, 운영체제 개념을 모른다는 전제로 작성한다.
- `버튼을 누르면 자동 생성된다`는 오해가 생기지 않도록 버튼명을 기능형이 아닌 안내형으로 작성한다.
- 사용자 화면에서 실제로 보이는 단어를 그대로 사용한다.
- 브라우저 UI 위치는 업데이트될 수 있으므로 `오른쪽 위`보다 `주소창 옆`처럼 상대적인 표현을 사용한다.

#애터미 상품명 포르투갈어 정리 작업 로그

## 작업 배경

브라질에서 사용할 애터미 가격표 앱의 상품명을 정리했다.

이 가격표는 사업자·센터장이 오프라인 행사나 고객 문의 상황에서 제품 가격을 바로 확인하기 위한 용도다. 따라서 공식 글로벌 영문명을 그대로 유지하는 것보다, 포르투갈어 사용자가 제품 종류를 빠르게 알아볼 수 있는 이름이 더 중요했다.

문제는 국가별 애터미 사이트마다 상품명이 다르게 제공된다는 점이었다.

- 한국 사이트: 한국어 공식 제품명
- 브라질 사이트: 목록에는 영어 상품명이 많음
- 브라질 상세 페이지: 일부 제품의 포르투갈어명이 이미지 안에만 있음
- 멕시코·콜롬비아 사이트: 스페인어 상품명 제공
- 국가별 상품 코드: 완전히 같지 않은 경우가 있음

---

## 처음 발견한 문제

처음에는 한국 상품 코드와 해외몰 상품 코드를 그대로 대조하면 될 것으로 생각했다.

하지만 실제로는 다음처럼 같은 제품인데 코드가 조금씩 달랐다.

- 한국 `000320` ↔ 브라질 `Q00321`
- 한국 `000330` ↔ 브라질 `Q00331`
- 한국 `000505` ↔ 브라질 `Q00501`

즉, 코드가 정확히 같지 않다고 해서 다른 상품으로 볼 수 없었다.

그래서 코드 매칭 결과를 다음처럼 구분하기로 했다.

- `exact_match`: 숫자 코드까지 동일
- `near_match`: 제품은 동일하지만 국가별 코드가 다름
- `not_found`: 해외몰에서 찾지 못함

추적용 열도 추가했다.

- `matched_code`
- `match_type`
- `name_source`
- `match_source_url`

## 국가별 상품명 수집

### 브라질 사이트

브라질몰은 상품 목록에 영어 이름이 많이 노출됐다.

하지만 상세 페이지의 제품 소개 이미지를 확인하면 일부 상품에 포르투갈어 제품명이 적혀 있었다. 이 텍스트는 웹페이지 본문이 아니라 이미지 안에 들어 있어서 일반 복사가 불가능했다.

Chrome OCR 확장 프로그램을 이용해 이미지를 직접 읽고 포르투갈어명을 수집했다.

문제점:

- 모든 상품에 포르투갈어명이 있는 것은 아님
- 일부 상품은 영어명만 존재
- 상품 목록과 상세 이미지의 이름이 다를 수 있음
- OCR로 하나씩 확인해야 해서 시간이 많이 걸림

### 멕시코 사이트

멕시코몰은 다른 국가몰보다 상품 목록 노출 방식과 코드 체계가 조금 더 까다로웠다.

- 멕시코 코드 앞에는 `X`가 붙음
- 숫자 코드가 한국과 동일한 제품도 있음
- 동일 제품인데 숫자 코드가 다른 경우도 있음
- 전체 상품이 한 화면에 모두 노출되지 않음

공식 상세 페이지까지 확인된 상품에 대해 스페인어명과 매칭 정보를 기록했다.

### 콜롬비아 사이트

콜롬비아몰은 멕시코몰보다 상품 목록과 상세 페이지 연결이 명확해서 비교적 수월했다.

- 콜롬비아 코드는 `O`로 시작
- 한국 코드와 같은 경우는 `exact_match`
- 동일 제품이지만 코드가 다른 경우는 `near_match`

콜롬비아 공식 스페인어명도 별도 열에 기록했다.

## 데이터 열 정리

최종적으로 상품명 관련 열을 다음처럼 구분했다.

- `name_ko`: 한국어 공식 제품명
- `name_pt`: 브라질 공식 포르투갈어 제품명
- `name_pt_eng`: 브라질 사이트에 텍스트로 노출된 공식 영어 제품명
- `name_es`: 멕시코·콜롬비아 공식 스페인어 제품명

공식명과 생성명을 섞지 않기 위해 번역 추적 열도 추가했다.

- `translation_basis`
- `translation_confidence`
- `translation_note`

번역 근거 예시:

- `official_br`: 브라질 공식 포르투갈어명
- `official_pt_pattern`: 브라질 공식 표현 패턴을 바탕으로 생성
- `official_es_to_pt`: 공식 스페인어명을 포르투갈어로 변환
- `brand_term_retained`: 브랜드·고유 제품명은 영어 유지
- `direct_translation`: 일반 제품 종류를 직접 번역

확신도:

- `official`
- `high`
- `medium`
- `low`

## 포르투갈어 명명 규칙

### 기본 원칙

상품명은 다음 구조로 정리했다.

`브랜드·라인명 + 포르투갈어 제품 종류`

예:

- `Absolute CellActive Toner` → `Absolute Tônico`
- `Deep Pure Cleansing Oil` → `Deep Pure Óleo de Limpeza`
- `Cerabebe Lotion` → `Cerabebe Loção`
- `Protein Intensive Treatment` → `Protein Intensive Máscara de Tratamento`

고유명은 유지하고, 제품 종류만 포르투갈어로 바꾸는 방식이다.

## Kids 제품군 정리

브라질 공식 표현에는 `Kids`와 `Infantil`이 혼재했다.

하지만 가격표에서는 알파벳 정렬과 검색 편의성이 더 중요했다.

따라서 모든 키즈 제품의 이름을 다음 규칙으로 통일했다.

`Kids + 포르투갈어 제품 종류`

예:

| 한국어 | 표시명 |
|---|---|
| 키즈 내추럴 치약 | Kids Creme Dental Natural |
| 키즈 비건 구미 멀티비타민 | Kids Multivitamínico Vegano em Gomas |
| 키즈 유산균 | Kids Probióticos |
| 키즈 츄어블 오메가3 | Kids Ômega 3 Mastigável |
| 키즈 칫솔 | Kids Escova Dental |
| 키즈 홍삼 | Kids Ginseng Vermelho |

이렇게 하면 모든 키즈 제품이 `K` 아래에 모이고, `Kids`, 제품 종류, 성분명으로 모두 검색할 수 있다.

## 최종 결과

- 브라질 공식 포르투갈어명은 그대로 보존
- 화장품·헤어·생활용품 중 빈칸은 공식 패턴을 바탕으로 생성
- 생성명마다 근거와 확신도를 기록
- 건강식품과 일반 식품은 무리하게 채우지 않고 보류
- 국가별 코드 차이는 `exact_match`와 `near_match`로 구분
- 제품군 고유명은 유지하고 일반 제품 종류만 포르투갈어로 변환
- Kids 제품은 검색과 정렬을 위해 `Kids` 접두어로 통일

## 오늘의 교훈

1. 같은 회사의 같은 제품이라도 국가별 상품 코드는 다를 수 있다.
2. 공식 사이트에 영어명만 보여도 상세 이미지 안에는 현지어명이 숨어 있을 수 있다.
3. 상품명 번역은 단어 하나씩 바꾸는 작업이 아니라 회사별 명명 패턴을 먼저 찾아야 한다.
4. 공식명과 생성명을 같은 열에 넣더라도 반드시 출처와 확신도를 추적해야 한다.
5. 사용자용 가격표에서는 완벽한 번역보다 검색성, 정렬, 즉시 이해가 더 중요하다.
6. OCR로 이미지 속 제품명을 하나씩 꺼내는 작업은 정말 끝이 없다.
7. 그래도 결국 다 했다.



# Worklog — iPhone 홈 화면 모드별 주소 분리

## 작업 배경

앱에는 다음 3가지 접근 모드가 있다.

1. 사업자
2. 센터
3. 관리자

Android에서는 각 모드별 manifest를 분리한 뒤 홈 화면 아이콘이 서로 다른 주소로 정상 저장되었다.

하지만 iPhone에서는 센터와 관리자 화면에서 홈 화면에 추가해도 모두 사업자 기본 주소인 아래 주소로만 저장되는 문제가 발생했다.

```text
https://price.nangok.app/
```

---

## 문제 확인

기존 주소 구조는 다음과 같았다.

```text
사업자
https://price.nangok.app/

센터
https://price.nangok.app/center/
→ 즉시 https://price.nangok.app/#/catalog/center 로 이동

관리자
https://price.nangok.app/admin/
→ 즉시 https://price.nangok.app/#/admin/ 로 이동
```

`/center/`, `/admin/`은 실제 앱 주소가 아니라 해시 라우트로 보내기 위한 리다이렉트 주소였다.

iPhone은 홈 화면에 추가할 때 manifest의 `start_url`보다 현재 Safari에서 열려 있는 실제 문서 URL을 기준으로 저장하는 경향이 있었다.

해시(`#`) 뒤 경로는 별도 문서 경로가 아니므로 다음 주소들은 모두 같은 루트 문서로 인식되었다.

```text
https://price.nangok.app/#/catalog/center
https://price.nangok.app/#/admin/
```

그 결과 센터와 관리자 아이콘도 모두 사업자 루트 주소로 저장되었다.

---

## 해결 방향

해시 라우팅 자체를 설치 주소로 사용하지 않고, 모드별로 실제 HTML 엔트리 주소를 분리하기로 했다.

목표 구조:

```text
사업자
https://price.nangok.app/

센터
https://price.nangok.app/center/

관리자
https://price.nangok.app/admin/
```

센터와 관리자 주소는 더 이상 `/#/...`로 이동하지 않고, 해당 주소를 유지한 채 React 앱을 직접 실행하도록 변경했다.

---

## 1차 수정

프로젝트 최상위에 별도 HTML 엔트리를 추가했다.

```text
ngcatalogue/
├─ admin/
│  └─ index.html
├─ center/
│  └─ index.html
├─ public/
├─ src/
├─ index.html
├─ package.json
└─ vite.config.ts
```

역할:

- `admin/index.html`: `/admin/`에서 관리자 앱 직접 실행
- `center/index.html`: `/center/`에서 센터 앱 직접 실행
- `index.html`: `/`에서 사업자 앱 실행

추가 변경:

- 관리자 manifest의 `start_url`, `id`, `scope`를 `/admin/` 기준으로 변경
- 센터 manifest의 `start_url`, `id`, `scope`를 `/center/` 기준으로 변경
- `App.tsx`에서 `window.location.pathname`을 기준으로 관리자·센터 모드 판별
- 서비스 워커 경로를 루트 기준 `/sw.js`로 고정
- Vite 다중 HTML 엔트리 빌드 구성
- 서비스 워커 캐시 버전 갱신
- TypeScript 및 Vite 프로덕션 빌드 확인

---

## 테스트 결과

센터 주소는 정상적으로 해결되었다.

```text
https://price.nangok.app/center/
```

위 주소가 더 이상 해시 주소로 바뀌지 않았고, iPhone 홈 화면에도 센터 주소로 정상 저장되었다.

하지만 관리자 주소는 여전히 아래처럼 동작했다.

```text
https://price.nangok.app/admin/
→ https://price.nangok.app/#/admin/
```

홈 화면 추가 시 주소도 다시 사업자 루트로 잡혔다.

---

## 관리자 주소만 실패한 원인

수정 파일과 기존 프로젝트를 합치는 과정에서 관리자용 `index.html`이 두 곳에 동시에 존재했다.

```text
admin/index.html
public/admin/index.html
```

각 파일의 역할은 달랐다.

```text
admin/index.html
새 관리자 앱 엔트리

public/admin/index.html
기존 /admin/ → /#/admin 리다이렉트 페이지
```

Vite 빌드 과정에서 `public` 폴더의 파일도 그대로 복사되기 때문에, 옛 `public/admin/index.html`이 새 관리자 엔트리와 충돌했다.

센터 쪽에도 동일한 형태의 옛 파일이 남아 있었다.

```text
public/center/index.html
```

---

## 최종 수정

아래 옛 리다이렉트 파일을 삭제했다.

```text
public/admin/index.html
public/center/index.html
```

최종 구조에서는 다음 파일만 실제 모드별 HTML 엔트리로 사용한다.

```text
admin/index.html
center/index.html
index.html
```

slash 없는 주소 처리를 위한 보조 리다이렉트 파일은 유지했다.

```text
public/admin.html
public/center.html
```

동작:

```text
/admin
→ /admin/

/center
→ /center/
```

중요한 점은 `/admin/`, `/center/`에 도달한 뒤 더 이상 해시 주소로 이동하지 않는 것이다.


기존에 만들어 둔 홈 화면 아이콘에는 이전 실행 주소가 저장되어 있으므로, 배포 후 기존 아이콘을 삭제하고 다시 추가해야 한다.

## 핵심 원인 요약

이번 문제는 manifest 분리 자체가 실패한 것이 아니라 다음 두 가지가 겹친 문제였다.

1. iPhone이 해시 라우트를 별도 설치 주소로 취급하지 않음
2. 옛 `public/admin/index.html` 리다이렉트 파일이 새 관리자 엔트리를 덮어씀

최종 해결은 manifest만 동적으로 바꾸는 방식이 아니라, 사업자·센터·관리자 각각에 실제 HTML 문서 경로를 부여하고 오래된 리다이렉트 파일을 제거하는 방식으로 이루어졌다.
